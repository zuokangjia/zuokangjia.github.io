Redis-101
2026-11-04 22:18:15 #redis

前阵子把 Redis 重新过了一遍。之前只会 SET、GET，这次顺手把持久化、内存淘汰和缓存那几个经典问题也理了理，记下来。

先想清楚拿来干嘛

Redis 是内存里的数据结构服务，本质上不是数据库。我目前用得上的场景：

  • 缓存热点数据，图的就是快
  • 计数器、排行榜、会话、分布式锁这种小的、高频的东西
  • 消息队列可以拿 Stream 凑合

不适合的也要知道：拿它当大号数据库塞冷数据，或者要复杂多表关联查询的场景，都不合适。

五种结构

  • String：缓存对象、INCR 计数
  • Hash：存对象的字段，比整个 JSON 字符串好改，能局部更新
  • List：简单队列，但用之前先想想积压了怎么办
  • Set：去重、交并差
  • ZSet：排行榜，按 score 排序

选结构之前先把 key 想好，我一般按 业务:实体:ID 写，后面排查、扫 key 都省事。

持久化：RDB 和 AOF

RDB 是快照，恢复快，但两次快照之间的数据可能丢。AOF 记的是写命令，数据更完整，文件更大、恢复也慢一点。

生产上常见的是两个都开：RDB 兜底快速恢复，AOF 负责少丢数据。具体哪个为主，看业务能接受丢多少。

内存满了怎么办

就两个配置：maxmemory 是上限，maxmemory-policy 是淘汰策略（比如 allkeys-lru）。

两个坑：

  • 不设过期时间，缓存早晚把内存吃满，变成“内存黑洞”
  • 大 key（超大 value、超长 list）不光占内存，读写和删除都会卡

缓存三件套

这块面试问得多，实际也容易出问题：

  • 缓存穿透：查一个本来就不存在的数据，请求全穿到 DB。布隆过滤器挡一层，查不到也缓存个空值，TTL 设短一点
  • 缓存击穿：某个热点 key 刚好过期，瞬间并发打到 DB。用互斥锁只放一个请求去回源，或者干脆逻辑过期、不删旧值
  • 缓存雪崩：一大批 key 同时过期。过期时间加随机抖动，再配合多级缓存

一些容易忽略的点

  • 缓存尽量都设 TTL，除了少数白名单
  • 命中率、内存、慢查询、连接数这几个指标盯住，出问题基本都能看出来
  • 线上不要 KEYS *，会阻塞，扫 key 用 SCAN
  • 大 key 定期查一查，能拆就拆
  • 改淘汰策略、改内存这种操作，先在压测环境按峰值 QPS 跑一遍
